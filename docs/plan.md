# BuildLog MVP 개발 계획

## 1. 계획의 목적

이 문서는 `spec.md`에 정한 기능을 어떤 순서로 개발할지 설명합니다.

처음 개발하는 과정에서 한 번에 너무 많은 내용을 다루지 않도록 작업을 작은 Phase로 나눕니다. 한 번의 작업에서는 Phase 하나만 진행하고, 확인 기준을 모두 통과한 뒤 다음 Phase로 넘어갑니다.

## 2. 개발 원칙

- `spec.md`에 없는 기능은 추가하지 않습니다.
- 각 Phase가 끝날 때 자동 테스트와 직접 화면 확인을 함께 수행합니다.
- 확인에 실패하면 다음 Phase로 넘어가지 않고 현재 Phase만 수정합니다.
- 화면에서 버튼을 숨기는 것만으로 권한을 처리하지 않습니다. 서버에서도 사용 권한을 검사합니다.
- 비밀번호와 비밀 설정값을 코드에 저장하거나 화면에 보여주지 않습니다.
- 실제 SQLite 데이터 파일, `.env`, `.venv`, 로그와 생성 파일은 Git 기록 대상에서 제외합니다.
- Git 초기화와 커밋은 별도 요청이 있기 전까지 수행하지 않습니다.
- 백엔드는 FastAPI, 프론트엔드는 React로 분리합니다. 필요한 외부 패키지만 사용합니다.
- 실제 서비스 DB는 Supabase의 PostgreSQL이며, 초기 로컬 개발과 자동 테스트에는 SQLite3를 사용합니다. DB 연결은 서버에서 관리하고 React는 FastAPI API로 데이터를 읽고 씁니다.
- SQLite3 테스트만으로 완료 처리하지 않습니다. Supabase에서도 마이그레이션, 검색, 제약 조건, 권한과 주요 흐름을 확인합니다.
- 회원가입·로그인과 비밀번호 검증은 FastAPI에서 직접 처리합니다. Supabase Auth는 사용하지 않으며 Supabase는 PostgreSQL DB로만 사용합니다. SQLite3 테스트에서도 동일한 인증·권한 로직을 검증합니다.

## 3. 예정된 프로젝트 구조

실제 개발을 시작하면 다음과 같이 역할을 나눕니다. 이름은 개발 중 임의로 바꾸지 않습니다.

```text
BuildLog/
├─ backend/
│  ├─ requirements.txt
│  ├─ app/
│  │  ├─ main.py       # FastAPI 시작점
│  │  ├─ core/         # 설정과 인증·권한 공통 처리
│  │  ├─ db/           # DB 연결과 공통 모델
│  │  ├─ accounts/     # 회원 API, 입력 검사, 모델
│  │  ├─ records/      # 공부 기록·할 일·오류 기록
│  │  └─ community/    # 댓글·좋아요·신고
│  ├─ migrations/      # DB 변경 이력
│  └─ tests/
├─ frontend/
│  ├─ package.json
│  └─ src/
│     ├─ pages/        # React 화면
│     ├─ components/   # 공통 UI
│     ├─ api/          # FastAPI 호출
│     └─ styles/       # CSS
├─ database/
│  └─ buildlog.test.sqlite3 # 로컬·테스트용, Git 제외
└─ docs/
```

## 4. 전체 개발 순서

| Phase | 만드는 결과 | 다음 Phase로 넘어가기 위한 핵심 조건 |
| --- | --- | --- |
| 0 | 개발 기준과 환경 확인 | 문서와 개발 환경에 충돌이 없음 |
| 1 | 실행 가능한 FastAPI·React 기본 구조 | 빈 서비스가 정상 실행됨 |
| 2 | 사용자 모델과 데이터베이스 시작점 | 첫 마이그레이션과 사용자 모델 테스트 통과 |
| 3 | 회원가입·로그인·닉네임 | 회원 기능과 접근 제한 테스트 통과 |
| 4 | 세 가지 기록의 데이터 구조 | 저장·재실행·제약 조건 테스트 통과 |
| 5 | 공부 기록 전체 흐름 | 공부 기록 기능만 단독으로 완성 |
| 6 | 할 일 전체 흐름 | 할 일 기능만 단독으로 완성 |
| 7 | 오류 기록 전체 흐름 | 오류 기록 기능만 단독으로 완성 |
| 8 | 공개 기록·공개 범위·공개 검색 | 비공개 유출 없이 공개 기능 동작 |
| 9 | 댓글 | 댓글 조건과 권한 테스트 통과 |
| 10 | 좋아요 | 중복 방지와 취소 테스트 통과 |
| 11 | 신고와 운영자 확인 | 신고 저장·중복 방지·운영자 권한 확인 |
| 12 | 반응형 화면과 공통 오류 처리 | 360px 이상 화면과 지정 브라우저 확인 |
| 13 | 전체 통합 확인과 실행 문서 | `spec.md`의 완료 조건 전체 통과 |

## 5. Phase별 상세 계획

### Phase 0. 개발 시작 전 기준 확인

#### 목표

코드나 패키지를 변경하기 전에 문서, 도구, 실행 환경과 인증 방식을 확인합니다.

#### 작업

1. `PRD.md`, `spec.md`, `plan.md`의 기능 범위와 충돌 여부를 확인합니다. 오류를 처음부터 해결 상태로 저장할 수 있는지 등 상충하는 문구는 사용자에게 확인합니다.
2. 제외 기능(이메일 확인, 비밀번호 찾기, 할 일 마감일·중요도·내 할 일 검색, 댓글 답글)을 확인합니다.
3. Python, Node.js, npm 실행 여부와 버전을 읽기 전용으로 확인하고 FastAPI·React와 호환되는 버전을 정합니다.
4. Python의 SQLite3 사용 가능 여부를 확인합니다.
5. 회원 인증은 FastAPI에서 직접 처리하는 것으로 확정합니다. 안전한 비밀번호 해시와 로그인 상태 유지 방식의 세부 구현을 정리합니다. Supabase는 PostgreSQL DB로만 사용하고 Supabase Auth는 사용하지 않습니다.
6. DB 접근과 변경 이력 관리 도구를 정합니다. SQLAlchemy와 Alembic을 후보로 검토하되 확정 전 설치하지 않습니다.
7. 개발 주소(백엔드 `http://127.0.0.1:8000`, 프론트엔드 `http://localhost:5173`), 허용할 프론트 주소(CORS), DB 파일 위치, 환경 변수 이름을 정리합니다. 포트 충돌 시 조정합니다.
8. 테스트·서버 실행 명령과 Supabase 연결 확인 절차를 `docs/setup.md`에 정리합니다.

#### 예상 변경 파일

- `docs/plan.md`, 필요 시 `docs/setup.md`
- 코드, 패키지, 실제 DB는 변경하지 않음

#### 확인 방법과 완료 조건

- 문서 충돌과 인증 방식 등 막히는 결정을 정리합니다.
- Python·Node.js·npm·SQLite3 상태를 확인합니다.
- 패키지 설치나 DB 생성 없이 결과를 공유하고 다음 Phase 진행 여부를 확인합니다.

### Phase 1. FastAPI와 React 기본 구조 만들기

#### 목표

FastAPI 서버와 React 화면을 실행하고 두 프로그램 사이의 API 연결을 확인합니다.

#### 작업

1. `backend/.venv`를 준비하고 FastAPI와 서버 실행에 필요한 패키지를 설치합니다. 정확한 버전을 `backend/requirements.txt`에 기록합니다.
2. `backend/app/main.py`와 공통 설정을 만듭니다.
3. React 개발 환경을 준비하고 `frontend/package.json`과 잠금 파일에 버전을 기록합니다. 빌드 도구는 Phase 0에서 확정합니다.
4. React 기본 화면과 FastAPI 상태 확인 API를 연결합니다.
5. CORS에는 개발에 사용하는 프론트엔드 주소만 허용합니다.
6. 서버의 `DATABASE_URL`로 SQLite3 테스트 DB와 Supabase PostgreSQL 연결을 구분하도록 설정합니다. 이 단계에서는 테이블과 마이그레이션을 만들지 않습니다.
7. 비밀값은 서버 환경 변수로 읽습니다. `.env.example`에는 필요한 항목 이름만 적습니다. React에는 API 주소 등 공개 가능한 값만 전달합니다.
8. `.gitignore`에 SQLite3 파일과 생성 파일 제외 규칙을 보완합니다.

#### 예상 변경 파일

- `backend/requirements.txt`, `backend/app/main.py`, `backend/app/core/`
- `frontend/package.json`, 프론트엔드 잠금 파일, `frontend/src/`
- `.env.example`, `.gitignore`, `docs/setup.md`

#### 확인 방법과 완료 조건

- 백엔드와 프론트엔드가 실행되고 React에서 상태 확인 API를 호출할 수 있습니다.
- 기본 화면과 CSS를 직접 확인하고 API 연결을 자동 테스트합니다.
- DB 테이블은 아직 생성하지 않습니다. 비밀값이 프론트엔드 번들과 코드에 포함되지 않아야 합니다.

### Phase 2. 사용자 모델과 첫 데이터베이스 만들기

#### 목표

이메일 로그인에 사용할 사용자 구조와 DB 변경 이력을 준비합니다.

#### 작업

1. `accounts` 사용자 모델과 FastAPI에서 직접 처리하는 인증 기반을 만듭니다.
2. 이메일과 닉네임은 필수이며 중복되지 않도록 합니다.
3. 닉네임은 2~20자이며 한글, 영문, 숫자, 밑줄만 허용합니다.
4. FastAPI에서 비밀번호를 안전한 해시로 변환하여 DB에 저장하고 로그인 시 검증합니다. 비밀번호 원문은 저장하거나 응답에 포함하지 않습니다.
5. 로그인 식별값은 이메일로 사용합니다. 운영자 권한을 일반 사용자와 구분할 수 있게 준비합니다.
6. 선택한 DB 도구로 첫 마이그레이션을 만들고 SQLite3 테스트 DB에 적용합니다.
7. Supabase 연결 정보가 준비되면 개발·검증용 PostgreSQL에도 적용하고 중복 제약과 사용자 저장을 확인합니다. 정보가 없으면 Supabase 검증은 미완료로 기록합니다.
8. 사용자 모델과 인증 방식에 맞는 단위 테스트를 작성합니다.

#### 예상 변경 파일

- `backend/app/accounts/`, `backend/app/core/`, `backend/app/db/`
- `backend/migrations/`, `backend/tests/test_accounts_models.py`
- `database/buildlog.test.sqlite3` (Git 제외)

#### 확인 방법과 완료 조건

- 이메일·닉네임 중복, 닉네임 조건, 비밀번호 안전 처리 테스트를 통과합니다.
- 재실행해도 사용자 데이터가 남아 있어야 합니다.
- DB를 지우지 않고 변경 이력으로 관리할 수 있어야 합니다.
- SQLite3와 Supabase 검증 결과를 각각 기록합니다. 준비되지 않은 Supabase 검증을 통과했다고 표시하지 않습니다.

### Phase 3. 회원가입·로그인·닉네임 변경

#### 목표

사용자가 계정을 만들고 로그인한 뒤 자신의 닉네임을 바꿀 수 있게 합니다.

#### 작업

1. 회원가입 API와 React 입력 화면을 만듭니다.
2. 이메일 형식, 중복 이메일, 비밀번호 8~64자, 닉네임 조건을 검사합니다.
3. 회원가입 실패 시 이메일과 닉네임은 유지하고 비밀번호만 지웁니다.
4. 성공하면 로그인 화면으로 이동합니다.
5. 로그인 API와 React 입력 화면을 만들고 이메일로 로그인하게 합니다.
6. 로그인 실패 시 이메일은 유지하고 비밀번호만 지웁니다.
7. 로그인 성공 시 내 기록 홈 화면으로 이동합니다.
8. 로그인하지 않은 사용자가 기록 화면에 접근하지 못하게 합니다.
9. 계정 설정에서 닉네임을 변경하게 합니다.
10. 공개 기록과 댓글에서 사용자 객체의 현재 닉네임을 읽도록 준비합니다.

#### 예상 변경 파일

- `backend/app/accounts/schemas.py`
- `backend/app/accounts/router.py`
- `backend/tests/`
- `backend/app/main.py`
- `frontend/src/pages/Signup.jsx`
- `frontend/src/pages/Login.jsx`
- `frontend/src/pages/AccountSettings.jsx`
- `frontend/src/pages/Home.jsx`

#### 확인 방법

- `spec.md`의 회원가입, 로그인, 닉네임 경계값을 자동 테스트합니다.
- 회원가입 성공 후 로그인 화면으로 이동하는지 확인합니다.
- 로그인 성공 후 내 기록 홈으로 이동하는지 확인합니다.
- 실패 시 유지하거나 지울 입력값이 정확한지 확인합니다.
- 로그인하지 않은 사용자가 기록 URL에 직접 접근해도 볼 수 없는지 확인합니다.
- 다른 사용자의 닉네임을 바꿀 수 없는지 확인합니다.

#### 완료 조건

- 회원 관련 자동 테스트와 직접 화면 확인이 모두 통과해야 합니다.
- 이메일 확인과 비밀번호 찾기 기능은 만들지 않습니다.

### Phase 4. 공부 기록·할 일·오류 기록의 데이터 구조

#### 목표

화면 작업 전에 세 가지 기록이 안전하게 저장될 공통 기반을 만듭니다.

#### 작업

1. 기록 기능 모듈을 만듭니다.
2. 공부 기록 모델을 만듭니다.
   - 작성자, 제목, 내용, 공개 여부
   - 작성 날짜·시간, 수정 날짜·시간
3. 할 일 모델을 만듭니다.
   - 작성자, 제목, 완료 여부, 공개 여부
   - 작성 날짜·시간, 수정 날짜·시간, 완료 날짜·시간
4. 오류 기록 모델을 만듭니다.
   - 작성자, 오류 제목, 오류 내용, 해결 방법, 해결 여부, 공개 여부
   - 작성 날짜·시간, 수정 날짜·시간, 해결 날짜·시간
5. 새 기록은 기본 비공개로 설정합니다.
6. 새 할 일은 미완료, 새 오류는 미해결로 설정합니다.
7. 제목과 내용의 최대 길이를 모델과 API 양쪽에서 검사할 수 있게 준비합니다.
8. 기록 작성자와 사용자 모델을 연결합니다.
9. 마이그레이션을 만들고 적용합니다.
10. 데이터 모델과 상태 전환 단위 테스트를 작성합니다.

#### 예상 변경 파일

- `backend/app/records/models.py`
- `backend/tests/test_models.py`
- `backend/migrations/`

#### 확인 방법

- 세 종류의 기록을 데이터베이스에 저장하고 다시 읽을 수 있는지 확인합니다.
- 기본 공개 상태와 기본 완료·해결 상태가 맞는지 확인합니다.
- 할 일 완료 시 완료 날짜가 생기고 취소 시 지워지는지 확인합니다.
- 오류 해결 시 해결 날짜가 생기고 미해결로 되돌리면 지워지는지 확인합니다.
- 오류를 미해결로 되돌려도 해결 방법은 유지되는지 확인합니다.

### Phase 13. 전체 통합 확인과 실행 문서 작성

#### 목표

처음 설치하는 사람도 실행할 수 있고, `spec.md`의 모든 기능이 함께 동작하는 상태로 마무리합니다.

#### 작업

1. FastAPI 자동 테스트, React 화면 테스트와 프론트엔드 빌드를 실행합니다.
2. SQLite3 테스트 외에 Supabase PostgreSQL에도 마이그레이션을 적용하고 검색·중복 제약·상태 전환·권한·데이터 유지를 확인합니다. 실제 사용자 데이터가 없는 검증 환경을 사용합니다.
3. 사용자 A, 사용자 B, 운영자 계정으로 권한 시나리오를 확인합니다.
4. 프로그램을 종료하고 다시 실행한 뒤 데이터 유지 여부를 확인합니다.
5. 비공개 기록이 목록, 검색, URL 직접 접근에서 노출되지 않는지 다시 확인합니다.
6. `spec.md`의 기능별 확인 항목을 처음부터 끝까지 실행합니다.
7. 설치, 환경 변수, 데이터베이스 준비, 서버 실행, 테스트 실행 방법을 문서로 작성합니다.
8. `.env.example`에 필요한 항목만 있고 비밀값이 없는지 확인합니다.
9. 실패한 항목만 수정하고 새 기능은 추가하지 않습니다.

## 6. 실제 진행 방법

1. 첫 작업은 Phase 0만 진행합니다.
2. Phase 0의 결과와 확인 내용을 공유합니다.
3. 사용자가 확인하면 Phase 1만 진행합니다.
4. 이후에도 같은 방식으로 Phase 하나씩 진행합니다.
5. 여러 Phase를 한 번에 구현하지 않습니다.
